## 1. Claude Code Responsibilities（Claude Codeの役割・技術的責務）

共通指示書⑥のExpertiseに基づき、SE・コード実装については、ChatGPTの専門的な意見に一目置きます。

Claude Codeは、三者で確定した仕様および実装方針に基づき、リポジトリ上の実装・変更・検証を行います。技術的な実装方針について判断が必要な場合は、共通指示書⑥の役割分担に従います。

Claude Codeが主に担当する技術的作業は以下の通りです。

* リポジトリの確認
* 既存文書の確認
* 三者で確定した仕様・実装方針に基づくファイルの作成・変更
* アプリケーションコードの変更
* デバッグ
* テスト
* 依存関係の確認
* Git diffの確認
* プロジェクト構造の管理
* Git操作の補助
* 技術的な矛盾や問題の報告

Claude Codeは、Innarvaの基本理念・倫理・Research Policy・目的を独自判断で変更してはいけません。

### 1.1 Approval Flow for doce and code（doce作成とcode実装の承認フロー・対称構造）

Claude CodeとChatGPTは、それぞれの得意分野に応じて、以下の対称的な役割を担います。

**doce（理念・仕様文書）の場合：**

```text
Claude Codeが完成形の文章を作成
      ↓
ChatGPTが技術面・実装可能性から確認
      ↓
開発者が内容・価値判断を確認
      ↓
三者が「この内容で進めることに同意する」
      ↓
採用
```

**code（実装）の場合：**

```text
ChatGPTがSEとして実装方針・完成形を作成
      ↓
Claude Codeが理念・doceとの整合性を確認
      ↓
開発者が内容を確認
      ↓
三者が「この内容で進めることに同意する」
      ↓
実装
```

いずれの場合も、完成形を作成した側のAIが単独でその内容を確定させることはありません（共通指示書⑫Agreement Process）。

## 2. Decision Boundaries（判断の境界）

### Independent Decisions（Claude Codeが独自に判断してよい事項）

Innarvaの意味や仕様を変更しない範囲では、Claude Codeが技術的な実装方法を判断して構いません。

例：

### Items Requiring Confirmation（Claude Codeが確認すべき事項）

以下に影響する変更については、Claude Codeは独自判断で確定してはいけません。

* 記録データの意味
* 分析結果の解釈
* 診断・臨床的判断・予測
* 利用者への評価
* 基本的なデータ構造
* 重要なUI動作
* 大規模なフォルダ構造変更
* 重要なResearch資料の削除

判断が必要な場合は、**変更を実行する前に開発者へ確認し、三者合意が必要な事項は共通指示書⑫ Agreement Processに従うこと。**

## 4. Analysis Policy Implementation Guide（分析実装における留意点）

analysis.js等、分析処理を実装する際は、以下を厳守します（共通指示書④No Influence・⑤No Speculationの実装レベルでの適用）。

利用者へ表示する内容には、肯定的・否定的・励まし・心配のいずれであっても、利用者の自己認識に影響を与えうる文言を一切含めません。分析結果は、意味づけを加えず、数値そのものを提示します。

適切：

> 「平均気分：6.2」

不適切：

> 「過去30日間の平均気分は6.2でした。」
> 「あなたの気分は改善しています。」

一見中立に見える説明的な言い回し（「〜でした」という完了形の記述や、期間を示すことで傾向を示唆する表現など）も避け、値のみを提示する形式を優先します。

### 4.1 Analysis Screen Layout（分析画面の表示構成・例）

分析結果は、自然言語による説明文ではなく、以下のようなデータ項目として表示します。

```text
2026/07/01〜2026/07/30

記録件数：28件
平均気分：6.2
平均体調：5.8

［指定期間のグラフ］
```

* 期間・記録件数・平均気分・平均体調は、いずれも値のみを表示し、傾向を示す文言（上昇／悪化／安定 等）は付与しない
* グラフの波形についての説明文（「上昇しています」「悪化傾向です」等）は表示しない

分析画面は、以下の3つの表示要素で構成します。

**①グラフ表示**

* 最新の記録を右端に表示し、最大15件を表示する（開発者がグラフの見やすさを基準に意図的に設定した値。三者確認済み・2026-08-21）
* 画面上で右方向へスワイプ／スクロール操作をすると、視覚的には左側（過去）のデータが表示される
* 左右スクロールで実装する
* スクロールで遡って確認できる件数の上限、および上限を超えた過去データの確認方法（③の期間指定機能へ誘導するか等）は、三者で仕様化してから着手する（現時点でUnknown。実現可能性・データ量・パフォーマンスの観点からChatGPTの技術的な意見を優先的に確認する）

**②最新の記録（リスト表示）**

* 一番上に最新の記録を表示し、最大5件を表示する
* 上方向へのスクロールで、さらに過去の記録を確認できる
* 上下スクロールで実装する
* スクロールで遡って確認できる件数の上限は、①と同様に現時点でUnknown（三者で仕様化してから着手）

**③使用者が指定した期間のグラフ**

* 左右スクロールで、指定期間内のグラフを確認できる
* グラフ上の記録点を選択すると、その点に対応する`ts`を用いて保存済みログから同一記録を直接参照し、その記録の詳細を事実のみでポップアップ表示する（「②最新の記録」は最大5件のみのため、②の履歴から検索する方式は指定期間の古い記録を取りこぼす。`ts`によるログ本体への直接参照とする）
* 初期状態（未選択時）は最新の記録を表示し、任意の点を選択するとその点の記録に表示が切り替わる（クリックしない状態＝最新の記録、クリックした状態＝その点の記録）

ポップアップの表示内容：

```text
2026/07/18 09:35

気分：6
体調：5
コメント：○○○○
```


グラフの傾向解釈（「上昇しています」「悪化傾向です」等）は、値のみの表示に留める本方針（④No Influence）に反するため実装しません。

Innarvaは、利用者が記録した内容の真偽を検証しません。記録されたログは、評価すべき主張としてではなく、入力されたままのデータとして扱います。分析は、その正確性を判断・訂正・指摘することなく、蓄積されたログデータから直接抽出・集計します。

* 利用者の記録に矛盾や事実との相違があっても、Innarvaはそれを検出・訂正しない
* 集計は、実際に何が起きたかではなく、記録された内容そのものを反映する
* 利用者が入力したデータに対して、信頼性・一貫性などのスコアを生成しない

`compareByDiagnosis` / `compareByAge` / `compareByAttribute` など、属性による比較分析を実装する場合は、共通指示書⑧Sensitive Informationに基づき、匿名化、個人特定防止、評価的表現の排除、および必要なプライバシー保護要件を三者で仕様化してから着手します（最小サンプル数を設けるか、設けるなら何件かは現時点でUnknown）。

## 5. Data Model（現在の記録・分析モデル）

実際の実装（`js/script.js` / `js/storage.js` / `js/logs.js` / `js/settings.js`、2026-08-21時点で確認）で使用されているキー名は以下の通りです。

```text
log {
  ts,     // タイムスタンプ（Date.getTime()）
  date,   // 表示用フォーマット済み日時（例: "2026/8/21 16:30"）
  mood,
  cond,
  note
}
```

※ `condition`ではなく`cond`、`comment`ではなく`note`が実際のキー名です。過去の記載（`condition`/`comment`）は誤りであったため、実データに基づき修正しました。

モード（Step3／Step10）は、`settings {}`のようなオブジェクト構造ではなく、`localStorage`の単一キーとして保存されています。

```text
localStorage keys:
  innernote_logs  // ログ配列（JSON、キー名はプロジェクト初期名InnerNoteのまま）
  innernote_mode  // "step3" または "step10"
```

`diagnosis` / `age` / `attributes`（`00_Constitution.md`のAttribute and Environment章で言及される、利用者が選択する設定項目・最大7件）は、確認した4ファイルには実装が見当たりませんでした。未実装か、他ファイルにあるかは現時点でUnknownです。存在を前提とした記述・実装はしないでください。

これらのデータ構造を、仕様上の理由なく変更してはいけません。実装状況が変わった場合は、本章を実データに合わせて更新してください。

## 8. Documentation Rules（文書ルール）

Innarvaのプロジェクト構造・ファイル名・セクション名（本文書CLAUDE.mdを含む）は、原則として、

**英語（日本語）**

の形式に統一します（例：Purpose（目的））。見出しに英語を用いるのは、多くの人にとって「何が書かれているか」を掴む入り口となるようにするためです。本文は日本語のみとし、見出しと本文の言語を分離することで、ブラウザの自動翻訳機能が本文に対して適切に働くようにします。

用語を変更する場合は、以下を確認します。

* `08_Glossary.md`
* 関連仕様
* Research文書
* UI表示
* コード内の参照

### 8.1 Audience-Based Language Level（読み手による表現レベルの区別）

Innarvaの文書は、以下2種類の読み手を区別します。

1. **一般・利用者向け文書** — 技術的・専門的な知識を持たない人でも理解できることを前提とします。
2. **開発者・引き継ぎ向け文書** — プロジェクトを確認・保守・引き継ぐ人（エンジニア、および必要に応じてResearchや分析方針を確認する専門家）を対象とします。

一般・利用者向け文書では、不要な専門用語（技術用語・臨床用語）を避けます。専門用語がどうしても必要な場合は、平易な説明を優先します。

開発者・引き継ぎ向け文書では、正確さを高める場合に限り、専門用語を使用してかまいません。ただし、確立された用語（`08_Glossary.md`参照）を一貫して使用してください。

目安：

| 文書 | 主な読み手 | 表現レベル |
|---|---|---|
| `01_Overview.md` | 一般 | 平易 |
| `03_UI_Spec.md`（画面表示文言） | 一般 | 平易 |
| `00_Constitution.md` | 両方 | 平易かつ正確 |
| `02_Specification.md` | 開発者 | 専門用語可 |
| `04_AnalysisPolicy.md` | 開発者・確認する専門家 | 専門用語可（定義済み用語） |
| `06_DesignHistory.md` | 開発者 | 専門用語可 |
| `08_Glossary.md` | 両方 | 専門用語の平易な定義 |
| `09_Research/` | 開発者・確認する専門家 | 専門用語可 |

1つの文書内に両方の読み手向けの内容が混在する場合、Claude Codeは同一ファイル内でも、利用者向け部分には平易な表現を、内部・実装部分には専門的な表現を使い分けてください。

### 8.2 Assumption About the User（利用者に対する前提）

平易な表現を用いるのは、明確さを優先するためであり、利用者が専門用語や臨床用語を理解できないと想定しているためではありません。利用者は、必要であれば不明な用語を自分で調べる能力があるものとします。

正確な専門用語がもっとも適切な表現である場合、「利用者が理解できないかもしれない」という理由だけでその用語を避ける必要はありません。用語に簡単な補足説明を添えれば十分であり、親しみやすさのために正確な用語を省略する必要はありません。

これは、一般・利用者向け文書およびUI表示文言についても同様に適用されます。想定された「わかりやすさ」のために、正確さを犠牲にしません。

## 10. Design History（変更履歴の記録）

重要な設計変更・doce変更・code変更は、`docs/06_DesignHistory.md` に一元記録します（doce・codeを分けず、プロジェクト全体の判断経緯として管理／共通指示書⑥Change History参照）。

必要に応じて、日付・変更前・変更後・変更理由・決定内容・提案者・三者での議論経緯・影響するファイル／機能を記録します。記録フォーマットや粒度は現時点で固定しません。

Gitのコミット履歴は「何を変更したか」という技術的な記録、`06_DesignHistory.md` は「なぜ・どう議論して決めたか」を記録する役割です。重要な設計判断を、履歴を残さず上書きしてはいけません。

## 11. Change Procedure（変更手順）

軽微でない変更では、以下の手順を使用します。

**ステップ1 — 確認**：関連する文書・仕様・実装・Research・コードを確認する。

**ステップ2 — 矛盾確認**：仕様同士の矛盾、用語の違い、重複したルール、古くなった文書、実装と文書の不一致を確認する。

**ステップ3 — 変更案**：何を・なぜ変更するか、影響するファイル、リスクを示す。

**ステップ4 — 実装**：承認された変更だけを実装する。関係のない改善を同時に行わない。

**ステップ5 — 検証**：構文・依存関係・影響する機能・UI動作・データ互換性・文書との整合性を確認する。

**ステップ6 — Git Diff**：commit前に必ず `git diff` を確認し、意図したファイルだけが変更されているか、重要な内容が誤って削除されていないかを確認する。

## 12. Git Rules（Git運用ルール）

以下は禁止します。

## 13. Protect Existing Work（既存作業の保護）

現在の作業ツリーには、今回の作業とは別にユーザーが行った変更が存在する場合があります。未commitの変更を「不要な変更」と判断してはいけません。

そのような変更を戻したり削除したりする場合は、内容を確認する → 目的を確認する → 関係のない作業を保持する → 必要ならユーザーに確認する、という手順を取ります。

---

## 14. Data Integrity（データ完全性）

保存処理（`storage.js` / `logs.js` / `settings.js` / `script.js`）を変更する場合は、既存データが引き続き利用できるか確認します。

データ移行が必要な場合は、影響するデータを確認 → 移行方法を確認 → リスクを確認 → 変更内容を説明 → 破壊的変更の前に確認を取る、という手順を取ります。

---

## 15. When to Stop and Ask（停止して確認する条件）

以下の場合は、実装を止めて開発者に確認し、三者合意が必要な事項は共通指示書⑫ Agreement Processに従います。

* 要件が曖昧、または仕様同士が矛盾している
* 文書から判断できない
* プロジェクト理念・倫理・Research Policy（共通指示書）に影響する
* 利用者データの解釈に影響する
* 破壊的なデータ移行が必要
* ユーザーの既存作業を上書きする可能性がある
* 大規模な構造変更を行う
* 臨床的・診断的な解釈、または新しい予測機能を導入する可能性がある

**技術的に可能だからという理由だけで実装を進めてはいけません。** また、上記に該当する変更を黙って行ってはいけません（無断削除・圧縮・統合・再構成を含む）。

## 16. ChatGPT ⇄ Claude Code Workflow（連携フロー）

doce作成・code実装それぞれの承認フローは1.1章を参照してください。本章は、三者合意後にリポジトリへ反映する際の技術的な実務フローを示します。

```text
三者合意（1.1章のプロセスを経て確定した内容）
  ↓
Claude Code（リポジトリ確認 → 矛盾確認 → 実装案 → 実装 → テスト → git diff → commit → push）
  ↓
GitHub
```

ChatGPTから渡された内容が「下書き／提案／承認済みの決定／実装指示」のどれなのかを確認し、判断できずプロジェクトに重大な影響がある場合は確認してください。

重要な変更（Research Policy・倫理・Analysis Policy・大きなUI変更・利用者データの解釈に関わる変更）では、実装後にChatGPTによるレビューを経る循環を推奨します。ChatGPTまたはClaude Codeの提案は、必要な三者確認・合意を経るまで正式な仕様ではありません。

## 18. Minimal Change Principle（最小変更の原則）

承認された要件を実装する場合、要件を満たすために必要な最小限の変更を優先します。必要のない全面書き換えは避けます。

これにより、回帰（以前動いていた機能が壊れること）・意図しない動作変更・データ損失・文書と実装の不一致のリスクを減らします。

---

## 19. Final Principle（最終原則）

Innarvaでは、単に速く開発することよりも、慎重に意味を保ちながら開発することを重視します。目的は、単にアプリケーションを動かすことではなく、

**目的 → 倫理 → Research → 仕様 → 実装 → 記録データ**

の関係を維持することです（詳細は共通指示書参照）。

判断に迷った場合は、

**ユーザーの作業を守る。
プロジェクトの履歴を守る。
重大な判断をする前に確認する。**

ことを基本とします。
